# Use local edge cache and request-driven maintenance

Bangumi X 将 Bangumi 公开资源的上游结果缓存在 Cloudflare Cache API 的当前数据中心，不建设跨数据中心的持久化公共数据镜像，并接受不同数据中心各自冷启动。Server 的所有 Bangumi API 调用，包括公开路由、放送快照和为个人数据校验的条目快照，都经过同一个统一资源加载器，由它执行按资源分类的软过期、硬过期、限时陈旧回退和短期 404 负缓存；同一实例内合并并发请求，上游并发上限为 4、每分钟最多发起 30 次请求，瞬时错误最多受控重试一次。后台工作（陈旧缓存重新验证、`waitUntil` 刷新和维护）不排队等待并发槽，每分钟最多占用一半额度，拿不到即放弃，把余量留给前台请求；个人页面每次请求最多延后刷新 4 个最旧的快照和 4 个放送，已确认完结的放送快照 30 天才刷新一次。公开 HTTP 响应缓存只作为资源缓存外层，HTML 缓存时间短于对应数据缓存时间。定时 Cron 被请求驱动维护替代：抽样公开请求尝试原子获取 D1 小时租约，每小时最多额外发起 2 次实际上游请求（缓存命中不计），优先逐步回填历史排行榜，剩余额度再刷新陈旧目录实体；一个季度需要拉取全部月份，回填游标只在该季度成功后前进，已拉到的月份留在缓存中供下次补全，因此冷季度约两小时完成，回填期间实体刷新相应放缓。同一租约还分批清理过期超过一天的会话、验证记录和账号关联请求，不发起上游请求。这样优先减少上游调用并适配 Cloudflare Free Tier，代价是跨数据中心冷未命中、低流量期间维护延迟，以及上游故障时在限定窗口内返回陈旧公开数据。用户私有状态不进入该缓存链路。
